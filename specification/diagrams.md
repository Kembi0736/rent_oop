# Диаграммы системы учёта аренды инструментов

> Отдельный файл к `specification.md`. Диаграммы построены по словарю (§1), таблице прав (§4) и сценариям (§7). Элементы, не подтверждённые текстом требования, помечены стереотипом `<<open>>` и пояснением — решения в диаграммы не добавляются.

---

## 1. Диаграмма классов

```mermaid
classDiagram
    direction LR

    class Клиент {
        +имя
        +контакт
        +оставитьЗаявку()
        +внестиЗалог()
        +вернутьИнструмент()
    }

    class Оператор {
        +обработатьЗаявку()
        +выдатьИнструмент()
        +принятьИнструмент()
        +проверитьДефекты()
        +вестиУчёт()
    }

    class Заявка {
        +статус
        +срок
        +обработать()
    }

    class Залог {
        +сумма
        +внести()
        +вернуть()
    }

    class Аренда {
        +начало
        +окончание
    }

    class Инструмент {
        <<тип>>
        +наименование
    }

    class ЕдиницаИнструмента {
        +инвентарныйНомер
        +состояние
    }

    class Дефект {
        +описание
    }

    class Запись {
        +дата
        +событие
    }

    Клиент "1" --> "0..*" Заявка : оставляет
    Клиент "1" --> "0..*" Залог : вносит
    Клиент "1" --> "0..*" Аренда : пользуется

    Заявка "1" --> "0..1" Залог : обеспечивается
    Заявка "1" --> "1" Инструмент : на

    Аренда "1" --> "1" ЕдиницаИнструмента : предмет
    Аренда "1" --> "0..*" Дефект : может иметь
    Аренда "1" --> "1" Залог : покрывается

    ЕдиницаИнструмента "0..*" --> "1" Инструмент : относится к типу

    Оператор "1" --> "0..*" Заявка : обрабатывает
    Оператор "1" --> "0..*" Аренда : выдаёт и принимает
    Оператор "1" --> "0..*" Дефект : фиксирует

    Запись "0..*" --> "1" Аренда : отражает
```

### Пояснения к классам (открытые вопросы)

| Элемент | Отметка |
|---|---|
| `Инструмент` / `ЕдиницаИнструмента` | `<<open>>` Требование не разделяет тип и экземпляр (словарь §1.2, вопрос 1–2). Разделение принято только для того, чтобы сценарий 7.4 (два клиента — одна лестница) был вообще формулируем. |
| `Заявка.статус` | `<<open>>` Состав статусов не определён (словарь §1.3). Значения взяты из сценариев §7: «ожидает обработки», «залог внесён», «обработана». |
| `Заявка.срок` | `<<open>>` Поле «на какой срок» упомянуто в словаре, единица измерения не определена. |
| `Залог.сумма` | `<<open>>` Способ определения суммы не определён (agent-log, вопрос 11). |
| `Залог.вернуть()` | `<<open>>` Полномочие на возврат отсутствует в таблице прав (замечание A2 проверки). |
| `Аренда.начало/окончание` | `<<open>>` Привязка к событиям «выдача»/«приём» следует из словаря, но начало отсчёта срока не определено (сценарий 7.1, шаг 4). |
| `Дефект` | `<<open>>` Связь «Дефект → удержание из залога» в требовании отсутствует; решение не моделируется. |
| `Оплата аренды` | `<<open>>` Сущность в словаре отсутствует; в диаграмму не включена (замечание A5). |
| `Запись` | `<<open>>` Словарь §1.6 допускает журнал, но его необходимость и формат не подтверждены. |
| Роли | По таблице прав (§4) рабочие роли только две: `Клиент` и `Оператор`. |

## 2. Диаграмма состояний

### 2.1. Состояния заявки

```mermaid
stateDiagram-v2
    [*] --> ОжидаетОбработки : клиент оставляет заявку

    ОжидаетОбработки --> ЗалогВнесён : клиент вносит залог
    ОжидаетОбработки --> Отклонена : <<open>> статус не определён

    ЗалогВнесён --> Обработана : оператор обрабатывает заявку

    Обработана --> [*] : выдача инструмента (переходит в аренду)

    Отклонена --> [*] : <<open>> возврат залога не определён

    note right of ОжидаетОбработки
        Статусы взяты из сценариев §7.
        Их состав словарём не подтверждён
        (словарь §1.3, открытый вопрос).
    end note

    note right of Отклонена
        <<open>> Возможность отклонения
        в требовании не упомянута (§3.2).
    end note
```

### 2.2. Состояния единицы инструмента

```mermaid
    stateDiagram-v2
    [*] --> Свободен

    Свободен --> ВАренде : выдача по заявке
    ВАренде --> Свободен : приём, дефектов не обнаружено

    ВАренде --> ДефектОбнаружен : <<open>> приём с дефектом

    ДефектОбнаружен --> Свободен : <<open>> возврат после устранения
    ДефектОбнаружен --> Списан : <<open>> не подлежит ремонту

    Списан --> [*]

    note right of ВАренде
        По тексту требования явно следуют
        только два состояния: «свободен»
        и «в аренде» (словарь §1.2).
    end note

    note right of ДефектОбнаружен
        <<open>> Состояние «неисправен» противоречит
        допущению 11 agent-log.md («статусов меньше трёх»).
        Отражено как замечание A1 проверки.
    end note
```

### 2.3. Состояния аренды (полный цикл из сценария 7.1)

```mermaid
stateDiagram-v2
    [*] --> Активна : выдача инструмента

    Активна --> Принята : клиент возвращает, оператор принимает
    Принята --> ЗалогВозвращён : оператор возвращает залог
    ЗалогВозвращён --> [*] : сделка закрыта

    note right of Принята
        <<open>> Шаги «принять» и «вернуть залог»
        разделены по сценарию 7.1,
        но допущение 15 agent-log.md принимает
        их за один шаг. Противоречие A3.
    end note
```

## 3. Связь с замечаниями проверки

- **A1** — состояние «неисправен» на диаграмме 2.2 помечено как `<<open>>` (противоречие со статусом допущения).
- **A3** — разделение «Принята → ЗалогВозвращён» на диаграмме 2.3 помечено как `<<open>>`.
- **A5** — оплата аренды отсутствует в классовой диаграмме, поскольку её существование не подтверждено.
- **B1** — действие «получить инструмент» в таблице прав отсутствует; на диаграмме классов его не создаём, выдача отнесена к оператору.
